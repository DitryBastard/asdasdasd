# AI Переводчик

Локальный ИИ-переводчик технической документации с собственной базой переведённых
документов (translation memory). Модель запускается полностью локально через
Ollama — тексты никуда не уходят.

## Как это устроено

```
frontend/  React + TypeScript интерфейс (перевод, база переводов)
backend/   FastAPI сервис: RAG-пайплайн перевода + база переводов на Chroma
Ollama     локальный сервер, отдаёт LLM (перевод) и embedding-модель (поиск)
```

Схема запроса на перевод:

1. Текст режется на предложения (с учётом языка, включая русский).
2. Каждое предложение превращается в embedding через Ollama (`bge-m3`).
3. Embedding ищется в локальной базе (Chroma) среди уже переведённых пар того
   же направления перевода.
4. По совпадению принимается решение:
   - **≥ 98% схожести** — предложение уже есть в базе почти дословно,
     сохранённый перевод используется как есть, модель не вызывается вообще.
     В интерфейсе это подсвечивается зелёным как «точное совпадение из базы».
   - **75–98% схожести** — найденная пара передаётся модели как референс
     терминологии/стиля в промпте, но перевод всё равно генерирует модель.
     Подсвечивается жёлтым как «похоже на запись из базы», с процентом схожести.
   - **< 75%** — совпадений нет, обычный перевод моделью.
5. Готовые пары сентенций собираются обратно в текст с сохранением абзацев.

Это честная механика: LLM не даёт токен-левел доказательств, "что она взяла
из базы", поэтому подсветка показывает не более и не менее того, что реально
происходит — какое совпадение было найдено и как оно использовано.

## Требования

- **Ollama** (https://ollama.com) — локальный сервер моделей.
- **Python 3.11+**
- **Node.js 18+**
- Видеокарта с достаточным объёмом VRAM (тестировалось в расчёте на RTX 5090,
  32 ГБ) — сам backend GPU не использует, всю инференс-нагрузку несёт Ollama.

### Модели

```bash
# Модель перевода. Qwen2.5 хорошо переводит технические тексты и уверенно
# работает с русским. На RTX 5090 можно выбрать более крупную модель.
ollama pull qwen2.5:14b-instruct     # быстрее, ~9 ГБ VRAM в Q4 — вариант по умолчанию
ollama pull qwen2.5:32b-instruct     # заметно качественнее, ~20 ГБ VRAM в Q4 — рекомендуется на 5090

# Embedding-модель для поиска по базе переводов — многоязычная, хорошо
# работает с русским и техническими терминами.
ollama pull bge-m3
```

Если возьмёте `qwen2.5:32b-instruct` вместо модели по умолчанию, укажите её в
`backend/.env` (см. ниже).

## Быстрый старт

### 1. Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # при необходимости отредактируйте модель/пороги
uvicorn app.main:app --reload --port 8000
```

Убедитесь, что Ollama уже запущена (`ollama serve`, обычно поднимается
автоматически после установки).

### 2. Frontend

```bash
cd frontend
npm install
npm run dev
```

Откройте адрес, который выведет Vite (обычно http://localhost:5173). Dev-сервер
проксирует `/api/*` на backend (`localhost:8000`), поэтому CORS настраивать не
нужно.

В шапке интерфейса виден статус подключения к Ollama и количество записей в
базе — если Ollama не отвечает, там будет явное предупреждение.

## Наполнение базы переводов

Вкладка «База переводов» даёт два способа пополнения:

- **Пара документов** (.docx / .pdf / .txt) — загружаете оригинал и готовый
  перевод, backend выравнивает абзацы друг с другом и показывает таблицу пар
  для проверки перед сохранением.

  Выравнивание смысловое, а не позиционное: каждый абзац с обеих сторон
  превращается в embedding (`bge-m3`), и по матрице схожести ищется лучший
  путь через обе последовательности динамическим программированием (тот же
  класс алгоритмов, что используют выравниватели параллельных корпусов вроде
  Vecalign). Поддерживаются не только пары 1:1, но и случаи, когда абзац
  пропущен, добавлен переводчиком или разбит/объединён при переводе — если
  для абзаца не нашлось пары, соответствующее поле в таблице предпросмотра
  остаётся пустым и подсвечивается, а не тихо сдвигает всё выравнивание
  дальше по документу (как было бы при сопоставлении по номеру абзаца).
  Пороги за это отвечающие (`ALIGNMENT_GAP_PENALTY`, `ALIGNMENT_MERGE_PENALTY`)
  — начальные разумные значения, не откалиброванные на реальных выдачах
  bge-m3; при необходимости их можно подстроить в `.env`.

  Этому шагу нужна работающая Ollama (используется для эмбеддингов) — раньше
  выравнивание было чисто позиционным и Ollama не требовало.

  **Таблицы выравниваются отдельно и по-другому.** Голое значение ячейки
  (символ элемента, число) само по себе не несёт почти никакого смысла,
  поэтому поиск по смысловой схожести для ячеек ненадёжен — а вот структура
  таблицы (строки/столбцы) при переводе сохраняется почти всегда. Поэтому
  ячейки таблиц сопоставляются по позиции (таблица N, строка M, столбец K с
  обеих сторон), а не по эмбеддингам, и извлекаются отдельно от текста
  абзацев — для .docx это родная структура таблиц python-docx, для PDF
  границы таблиц определяются библиотекой `pdfplumber` (по линиям
  таблицы), и найденная область исключается из текста абзацев, чтобы
  содержимое таблицы не попадало в выдачу дважды.

- **Ручное добавление** — быстро добавить одну пару термин/фраза → перевод,
  без файлов.

При сохранении пары каждый абзац дополнительно разбивается на предложения;
если количество предложений в оригинале и переводе совпадает, в базу
попадают более точные пары на уровне предложений (лучше для последующего
поиска), иначе — весь абзац целиком.

## Скачивание перевода в исходном форматировании

На вкладке «Перевод», после загрузки и перевода файла **.docx**, появляется
кнопка «Скачать .docx с оригинальным форматированием». Она пересобирает
исходный документ, подставляя перевод в каждый абзац (включая ячейки таблиц)
и сохраняя стиль абзаца (заголовок, список, шрифт/начертание первого рана).

Важная оговорка: форматирование сохраняется на уровне абзаца целиком, а не
отдельных слов внутри него — если жирным было одно слово в середине
предложения, после перевода жирным станет весь абзац. Точного решения для
этого не существует в принципе: слова перевода не соответствуют один к
одному словам оригинала, поэтому невозможно однозначно определить, на какой
именно фрагмент перевода должно было бы перенестись форматирование. Так же
поступают все основные CAT-инструменты.

Для **PDF** кнопка не показывается — точное воспроизведение исходной вёрстки
PDF с переводом (обычно другой длины, чем оригинал) ненадёжная задача, результат
будет визуально хуже, чем просто текст. Если нужен PDF на основе перевода —
переведите текст на вкладке «Перевод» и оформите его отдельно вручную, либо
попросите добавить экспорт в чистый .docx без попытки повторить исходную PDF-вёрстку.

## Конфигурация (`backend/.env`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | адрес Ollama |
| `OLLAMA_CHAT_MODEL` | `qwen2.5:14b-instruct` | модель перевода |
| `OLLAMA_EMBED_MODEL` | `bge-m3` | модель эмбеддингов |
| `CHROMA_PERSIST_DIR` | `./data/chroma` | где хранится база переводов на диске |
| `EXACT_MATCH_THRESHOLD` | `0.98` | порог "точного" совпадения |
| `FUZZY_MATCH_THRESHOLD` | `0.75` | порог "похожего" совпадения |
| `TOP_K_MATCHES` | `3` | сколько кандидатов рассматривать на предложение |
| `BATCH_SIZE` | `20` | сколько предложений уходит в модель за один запрос |
| `ALIGNMENT_GAP_PENALTY` | `0.15` | штраф за абзац без пары при выравнивании документов |
| `ALIGNMENT_MERGE_PENALTY` | `0.03` | штраф за объединение двух абзацев в один при выравнивании |
| `PDF_TEXT_X_TOLERANCE` | `1.5` | чувствительность к пробелам между словами при извлечении текста PDF |
| `CORS_ORIGINS` | `http://localhost:5173` | разрешённые origin для API |

## Тесты

```bash
cd backend
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest
```

Тесты покрывают чистую логику (разбиение на предложения, классификацию
совпадений, разбор пронумерованных ответов модели, DP-выравнивание абзацев
по эмбеддингам, позиционное выравнивание ячеек таблиц, распознавание таблиц
в PDF через pdfplumber на сгенерированном тестовом файле, сборку .docx с
переводом) и сквозную проверку API-маршрутов с подменённым Ollama-клиентом —
без обращения к реальной модели или GPU.

## Известные ограничения

- Пороги выравнивания абзацев (`ALIGNMENT_GAP_PENALTY`/`ALIGNMENT_MERGE_PENALTY`)
  подобраны по замыслу алгоритма, а не откалиброваны на реальных эмбеддингах
  bge-m3 — на живых документах может понадобиться подстройка в `.env`.
- Эмбеддинги для объединённых абзацев (1:2 / 2:1) приближаются усреднением
  эмбеддингов исходных абзацев, а не эмбеддингом склеенного текста — так же
  поступают промышленные выравниватели корпусов по той же причине (иначе
  пришлось бы эмбеддить все возможные сочетания абзацев).
- Распознавание таблиц в PDF (`pdfplumber`) полагается на видимые линии
  таблицы; таблицы без рамок/линий (только пробелами разделённые колонки)
  может не распознать как таблицу и тогда её содержимое попадёт в общий
  текст абзацев как обычные строки — в этом случае для этих строк снова
  включится (менее подходящее) смысловое выравнивание.
- Выравнивание ячеек таблиц позиционное: таблица N ↔ таблица N по порядку
  следования, строка/столбец такие же. Если переводчик добавил, убрал или
  переставил местами строки/столбцы таблицы, позиционное соответствие
  собьётся для этой таблицы — как и при пропущенном абзаце, это будет видно
  в предпросмотре как незаполненная пара, а не тихая ошибка.
- Извлечение текста из PDF (вне таблиц) режется на абзацы по пустым строкам
  постранично; если на конкретной странице пустых строк нет (частый случай
  в плотно свёрстанных технических документах — раньше это приводило к
  разбиению по каждой физической строке, т.е. к сотням мусорных фрагментов
  вместо десятка настоящих абзацев), вся страница трактуется как один
  абзац — грубее, но не разваливает выравнивание. Для сложных
  многоколоночных макетов качество извлечения ниже, чем для .docx.
- Разделение текста PDF на слова (`PDF_TEXT_X_TOLERANCE`) — эвристика по
  зазору между символами; на конкретном шрифте/PDF-генераторе слова могут
  склеиваться без пробела ("wasdevelopedin") или наоборот разбиваться
  лишними пробелами. Значение по умолчанию — разумная отправная точка, не
  проверенная на вашем конкретном документе; если увидите склеенные слова
  или лишние пробелы на реальном файле — подстройте `PDF_TEXT_X_TOLERANCE`
  в `.env` (меньше значение — чувствительнее к узким зазорам) и загрузите
  документ заново.
- Скачивание с оригинальным форматированием поддерживается только для .docx
  и только на уровне абзаца целиком (см. раздел выше) — для PDF не
  предлагается принципиально, чтобы не выдавать хрупкий, визуально
  испорченный результат.
- Backend не проверялся с реальной Ollama и GPU в среде разработки (в этом
  окружении нет видеокарты) — вся сетевая логика проверена тестами с
  подменённым клиентом, но перед первым реальным использованием стоит
  прогнать пару переводов вручную и свериться с ожиданиями.

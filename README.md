# AI Переводчик

Локальный ИИ-переводчик технической документации с собственной базой переведённых
документов (translation memory). Модель запускается полностью локально через
Ollama — тексты никуда не уходят.

## Как это устроено

```
frontend/  React + TypeScript интерфейс (перевод, база переводов, термбаза)
backend/   FastAPI сервис: RAG-пайплайн перевода + база переводов на Chroma + термбаза (JSON)
Ollama     локальный сервер, отдаёт LLM (перевод) и embedding-модель (поиск)
```

Схема запроса на перевод:

1. Текст режется на предложения (с учётом языка, включая русский).
2. Каждое предложение превращается в embedding через Ollama (`bge-m3`).
3. Embedding ищется в локальной базе (Chroma) среди уже переведённых пар того
   же направления перевода.
4. По совпадению принимается решение:
   - **≥ 98% схожести** — предложение уже есть в базе почти дословно,
     сохранённый перевод используется как есть, модель не вызывается вообще.
     В интерфейсе это подсвечивается зелёным как «точное совпадение из базы».
   - **75–98% схожести** — найденная пара передаётся модели как референс
     терминологии/стиля в промпте, но перевод всё равно генерирует модель.
     Подсвечивается жёлтым как «похоже на запись из базы», с процентом схожести.
   - **< 75%** — совпадений нет, обычный перевод моделью.
5. Если предложение всё же уходит модели (т.е. не сработало точное
   совпадение из шага 4), в промпт дополнительно подмешиваются обязательные
   термины из термбазы — отдельного от базы переводов хранилища (см. раздел
   «Термбаза» ниже).
6. Готовые пары сентенций собираются обратно в текст с сохранением абзацев.
7. Каждый сегмент дополнительно прогоняется через автоматическую QA-проверку
   (см. «Автоматическая проверка перевода» ниже) — по её результату сегмент
   может получить предупреждение независимо от того, откуда взят перевод.

Это честная механика: LLM не даёт токен-левел доказательств, "что она взяла
из базы", поэтому подсветка показывает не более и не менее того, что реально
происходит — какое совпадение было найдено и как оно использовано.

## Требования

- **Ollama** (https://ollama.com) — локальный сервер моделей.
- **Python 3.11+**
- **Node.js 18+**
- Видеокарта с достаточным объёмом VRAM (тестировалось в расчёте на RTX 5090,
  32 ГБ) — сам backend GPU не использует, всю инференс-нагрузку несёт Ollama.

### Модели

```bash
# Модель перевода. Qwen2.5 хорошо переводит технические тексты и уверенно
# работает с русским. На RTX 5090 можно выбрать более крупную модель.
ollama pull qwen2.5:14b-instruct     # быстрее, ~9 ГБ VRAM в Q4 — вариант по умолчанию
ollama pull qwen2.5:32b-instruct     # заметно качественнее, ~20 ГБ VRAM в Q4 — рекомендуется на 5090

# Embedding-модель для поиска по базе переводов — многоязычная, хорошо
# работает с русским и техническими терминами.
ollama pull bge-m3
```

Если возьмёте `qwen2.5:32b-instruct` вместо модели по умолчанию, укажите её в
`backend/.env` (см. ниже).

## Быстрый старт

### 1. Backend

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env               # при необходимости отредактируйте модель/пороги
uvicorn app.main:app --reload --port 8000
```

Убедитесь, что Ollama уже запущена (`ollama serve`, обычно поднимается
автоматически после установки).

### 2. Frontend

```bash
cd frontend
npm install
npm run dev
```

Откройте адрес, который выведет Vite (обычно http://localhost:5173). Dev-сервер
проксирует `/api/*` на backend (`localhost:8000`), поэтому CORS настраивать не
нужно.

В шапке интерфейса виден статус подключения к Ollama и количество записей в
базе — если Ollama не отвечает, там будет явное предупреждение.

## Наполнение базы переводов

Вкладка «База переводов» даёт два способа пополнения напрямую (плюс TMX-импорт
и правку перевода на вкладке «Перевод» — см. соответствующие разделы ниже):

- **Пара документов** (.docx / .pdf / .txt) — загружаете оригинал и готовый
  перевод, backend выравнивает их друг с другом и показывает таблицу пар для
  проверки перед сохранением.

  Разбиение на смысловые куски и их сопоставление делает сама модель
  (`OLLAMA_CHAT_MODEL`) за один шаг, а не два отдельных: сначала правила
  режут текст на «абзацы», потом что-то их сопоставляет. Так было раньше
  (сначала по пустым строкам, потом по эмбеддингам через динамическое
  программирование) — и оба варианта регулярно ошибались, потому что
  реальные технические документы вперемешку содержат сплошную прозу,
  короткие пункты списков (например, перечень стандартов) и заголовки, а
  унифицированного правила, которое одинаково хорошо режет все три вида
  текста, не существует. Модели вместо этого просто отдаётся весь текст
  документа (постранично объединённый, без разбиения на абзацы), она сама
  видит, где проза, где список, где заголовок, и возвращает готовые пары в
  JSON. Если документ большой, текст делится на смысловые куски по лимиту
  символов (`LLM_ALIGNMENT_MAX_CHARS`) — по возможности на границах абзацев/
  предложений — и выравнивается по частям, куски с одним и тем же номером
  на обеих сторонах отправляются в модель за один вызов; если у модели не
  получилось вернуть корректный JSON для куска — весь кусок с обеих сторон
  сохраняется как одна грубая пара, а не теряется.

  Если для куска не нашлось пары, соответствующее поле в таблице
  предпросмотра остаётся пустым и подсвечивается — впишите перевод вручную
  или удалите строку перед сохранением.

  **Таблицы выравниваются отдельно и по-другому**, без участия модели.
  Голое значение ячейки (символ элемента, число) само по себе не несёт
  почти никакого смысла, чтобы модель или поиск по схожести могли его
  надёжно распознать — а вот структура таблицы (строки/столбцы) при
  переводе сохраняется почти всегда. Поэтому ячейки таблиц сопоставляются
  по позиции (таблица N, строка M, столбец K с обеих сторон) и
  извлекаются отдельно от текста — для .docx это родная структура таблиц
  python-docx, для PDF границы таблиц определяются библиотекой `pdfplumber`
  (по линиям таблицы), и найденная область исключается из текста абзацев,
  чтобы содержимое таблицы не попадало в выдачу дважды.

- **Ручное добавление** — быстро добавить одну пару термин/фраза → перевод,
  без файлов.

При сохранении пары каждый абзац дополнительно разбивается на предложения;
если количество предложений в оригинале и переводе совпадает, в базу
попадают более точные пары на уровне предложений (лучше для последующего
поиска), иначе — весь абзац целиком.

## Термбаза (глоссарий) — отдельно от базы переводов

Вкладка «Термбаза» — это второе, самостоятельное хранилище, которое легко
спутать с базой переводов, но у них разное назначение:

- **База переводов** (Chroma, векторный поиск по схожести) отвечает на
  вопрос «похоже ли это предложение на то, что мы уже когда-то переводили» —
  подходит для целых предложений, где важен смысл в целом, а не точное
  совпадение по буквам.
- **Термбаза** отвечает на другой вопрос: «этот конкретный термин всегда
  обязан переводиться именно так» — жёсткое ограничение, которое поиск по
  смысловой схожести в принципе не может гарантировать (два варианта
  перевода термина могут быть семантически одинаково близки, а с точки
  зрения принятой терминологии/фирменного стиля правильный только один).

Поэтому термбаза устроена по-другому и технически: это не Chroma, а простой
JSON-файл (`GLOSSARY_PATH`) с ручным списком пар термин → перевод, а поиск
применимых терминов для предложения — точное вхождение подстроки
(регистронезависимое), а не векторный поиск. Для небольшого куратируемого
списка терминов это надёжнее и прозрачнее, чем similarity-поиск.

Термины из термбазы попадают в промпт модели как обязательное правило
(«переведи точно так, без исключений») в тех же случаях, когда модель вообще
вызывается — то есть на предложения, для которых сработало **точное**
совпадение из базы переводов (шаг 4 схемы выше, сохранённый перевод
используется как есть без вызова модели), термбаза не влияет: этот перевод
уже подтверждён человеком ранее и не проходит через модель заново.

Добавить/удалить термин можно на вкладке «Термбаза», отдельно для каждой
пары языков.

## Автоматическая проверка перевода и правка перед сохранением

Каждый переведённый сегмент проходит через набор простых, но целенаправленных
проверок (`app/qa_checks.py`) сразу после перевода — независимо от того,
переведён он моделью или взят из базы как точное совпадение:

- **Пустой перевод** — модель вернула пустую строку.
- **Перевод дословно совпадает с оригиналом** — похоже, что сегмент не
  перевели, а оставили как есть (проверяется только для сегментов, где
  вообще есть буквы — короткие коды/номера, которые действительно не должны
  меняться, не считаются).
- **Числа в переводе не совпадают с оригиналом** — набор чисел в переводе
  (после нормализации `.`/`,` как десятичного разделителя) отличается от
  набора чисел в оригинале — частый и особенно дорогой тип ошибки в
  технической документации.

Это осознанно немного проверок с низкой долей ложных срабатываний, а не
попытка полной лингвистической QA — цель заметить, когда стоит проверить
сегмент вручную, а не заменить вычитку человеком. Сегменты с предупреждением
подчёркиваются в интерфейсе волнистой линией; клик по сегменту показывает,
что именно не так.

На вкладке «Перевод» кнопка «✎ Просмотр и правка» переключает вывод в
двухколоночную таблицу оригинал/перевод, где перевод каждого сегмента можно
исправить прямо в текстовом поле (например, по QA-предупреждению или просто
на глаз). После правок кнопка «Сохранить перевод в базу» отправляет все
непустые пары в базу переводов той же командой, что и подтверждение пар
документов на вкладке «База переводов» — то есть это ещё один способ
пополнить базу, дополняющий пары документов и ручной ввод.

## Экспорт/импорт базы переводов (TMX)

Вкладка «База переводов» содержит блок экспорта/импорта в формате **TMX**
(Translation Memory eXchange, TMX 1.4b) — отраслевом XML-формате обмена
базами переводов, который понимают основные CAT-инструменты (Trados, memoQ,
OmegaT и другие). Это значит, что база, накопленная в этом приложении, не
заперта внутри него:

- **Экспорт** выгружает всю базу переводов целиком в один `.tmx`-файл —
  можно использовать как бэкап или перенести базу в другой инструмент.
- **Импорт** добавляет пары из `.tmx`-файла (например, экспортированного из
  другого CAT-инструмента) в локальную базу для указанной пары языков.
  Каждый `<tu>` может содержать больше двух `<tuv>` (многоязычная память) —
  используются только варианты с языками, совпадающими с выбранной парой
  (тег языка сравнивается по основному подтегу: `en`, `en-US` и `en-GB`
  считаются одним и тем же). Импортированные пары проходят тот же путь, что
  и пары из документов: если оригинал и перевод одной пары одинаково
  делятся на предложения, в базу попадают предложения, иначе — весь
  сегмент `<tu>` целиком.

Повреждённый или не-TMX файл при импорте отклоняется с понятным сообщением
об ошибке, база при этом не изменяется.

## Скачивание перевода в исходном форматировании

На вкладке «Перевод», после загрузки и перевода файла **.docx**, появляется
кнопка «Скачать .docx с оригинальным форматированием». Она пересобирает
исходный документ, подставляя перевод в каждый абзац (включая ячейки таблиц)
и сохраняя стиль абзаца (заголовок, список, шрифт/начертание первого рана).

Важная оговорка: форматирование сохраняется на уровне абзаца целиком, а не
отдельных слов внутри него — если жирным было одно слово в середине
предложения, после перевода жирным станет весь абзац. Точного решения для
этого не существует в принципе: слова перевода не соответствуют один к
одному словам оригинала, поэтому невозможно однозначно определить, на какой
именно фрагмент перевода должно было бы перенестись форматирование. Так же
поступают все основные CAT-инструменты.

Для **PDF** кнопка не показывается — точное воспроизведение исходной вёрстки
PDF с переводом (обычно другой длины, чем оригинал) ненадёжная задача, результат
будет визуально хуже, чем просто текст. Если нужен PDF на основе перевода —
переведите текст на вкладке «Перевод» и оформите его отдельно вручную, либо
попросите добавить экспорт в чистый .docx без попытки повторить исходную PDF-вёрстку.

## Конфигурация (`backend/.env`)

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `OLLAMA_BASE_URL` | `http://localhost:11434` | адрес Ollama |
| `OLLAMA_CHAT_MODEL` | `qwen2.5:14b-instruct` | модель перевода |
| `OLLAMA_EMBED_MODEL` | `bge-m3` | модель эмбеддингов |
| `CHROMA_PERSIST_DIR` | `./data/chroma` | где хранится база переводов на диске |
| `GLOSSARY_PATH` | `./data/glossary.json` | где хранится термбаза (глоссарий), отдельно от базы переводов |
| `EXACT_MATCH_THRESHOLD` | `0.98` | порог "точного" совпадения |
| `FUZZY_MATCH_THRESHOLD` | `0.75` | порог "похожего" совпадения |
| `TOP_K_MATCHES` | `3` | сколько кандидатов рассматривать на предложение |
| `BATCH_SIZE` | `20` | сколько предложений уходит в модель за один запрос |
| `LLM_ALIGNMENT_MAX_CHARS` | `12000` | сколько символов текста уходит модели за один вызов при выравнивании документов |
| `PDF_TEXT_X_TOLERANCE` | `1.5` | чувствительность к пробелам между словами при извлечении текста PDF |
| `CORS_ORIGINS` | `http://localhost:5173` | разрешённые origin для API |

## Тесты

```bash
cd backend
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest
```

Тесты покрывают чистую логику (разбиение на предложения, классификацию
совпадений, разбор пронумерованных ответов модели, разбиение документа на
куски для выравнивания и разбор JSON-ответа модели, позиционное
выравнивание ячеек таблиц, распознавание таблиц в PDF через pdfplumber на
сгенерированном тестовом файле, сборку .docx с переводом, QA-проверки
сегментов, хранилище термбазы, сборку и разбор TMX) и сквозную проверку
API-маршрутов с подменённым Ollama-клиентом — включая то, что термины из
термбазы действительно попадают в промпт модели, и полный цикл
экспорт→импорт TMX — без обращения к реальной модели или GPU. Это значит,
что сама точность выравнивания и перевода (насколько хорошо модель на самом
деле сегментирует/сопоставляет текст или переводит конкретное предложение)
здесь не проверена — тесты гарантируют, что конвейер работает и корректно
разбирает ответ модели в ожидаемом формате, но не судят о качестве самого
выравнивания или перевода на живых документах.

## Известные ограничения

- Выравнивание документов теперь целиком полагается на способность модели
  вернуть корректный JSON и разумно сегментировать/сопоставить текст.
  Локальные модели меньшего размера могут справляться с этим хуже, чем с
  собственно переводом — если увидите, что выравнивание сходит с рельс на
  большом/сложном документе, попробуйте модель покрупнее (см. рекомендации
  моделей выше) или уменьшите `LLM_ALIGNMENT_MAX_CHARS`, чтобы модель
  обрабатывала за раз меньше текста.
- Если модель не вернула корректный JSON для какого-то куска документа
  (после единственной попытки, без повторного запроса) — весь этот кусок
  сохраняется как одна грубая пара целиком с обеих сторон, а не пропадает;
  такую пару стоит перепроверить в предпросмотре отдельно.
- Разбиение документа на куски по `LLM_ALIGNMENT_MAX_CHARS` не гарантирует,
  что кускам с одинаковым номером на обеих сторонах реально соответствует
  одно и то же место в документе — это предположение верно, если перевод
  примерно пропорционален оригиналу по всему документу, но может не
  сработать для документов с очень неравномерной плотностью текста между
  разделами.
- Распознавание таблиц в PDF (`pdfplumber`) полагается на видимые линии
  таблицы; таблицы без рамок/линий (только пробелами разделённые колонки)
  может не распознать как таблицу, и тогда её содержимое попадёт в общий
  текст документа как обычные строки, наравне с прозой.
- Выравнивание ячеек таблиц позиционное: таблица N ↔ таблица N по порядку
  следования, строка/столбец такие же. Если переводчик добавил, убрал или
  переставил местами строки/столбцы таблицы, позиционное соответствие
  собьётся для этой таблицы — как и при несопоставленном куске текста, это
  будет видно в предпросмотре как незаполненная пара, а не тихая ошибка.
- Извлечение текста из PDF для перевода (`/api/translate/document`, вне
  этого шага выравнивания) по-прежнему режется на абзацы по пустым строкам
  постранично, с откатом на «вся страница — один абзац», если пустых строк
  нет; для сложных многоколоночных макетов качество извлечения ниже, чем
  для .docx.
- Разделение текста PDF на слова (`PDF_TEXT_X_TOLERANCE`) — эвристика по
  зазору между символами; на конкретном шрифте/PDF-генераторе слова могут
  склеиваться без пробела ("wasdevelopedin") или наоборот разбиваться
  лишними пробелами. Значение по умолчанию — разумная отправная точка, не
  проверенная на вашем конкретном документе; если увидите склеенные слова
  или лишние пробелы на реальном файле — подстройте `PDF_TEXT_X_TOLERANCE`
  в `.env` (меньше значение — чувствительнее к узким зазорам) и загрузите
  документ заново.
- Скачивание с оригинальным форматированием поддерживается только для .docx
  и только на уровне абзаца целиком (см. раздел выше) — для PDF не
  предлагается принципиально, чтобы не выдавать хрупкий, визуально
  испорченный результат.
- Автоматические QA-проверки (`app/qa_checks.py`) — это несколько
  целенаправленных эвристик (пустой перевод, дословное совпадение с
  оригиналом, несовпадение чисел), а не полноценная лингвистическая
  проверка. Предупреждение — повод посмотреть сегмент глазами, а не
  доказанная ошибка; и наоборот, отсутствие предупреждений не гарантирует,
  что перевод корректен по смыслу.
- Термбаза ищет применимые термины точным вхождением подстроки без учёта
  морфологии: если в термбазе сохранено «сервопривод», а в предложении
  встречается словоформа «сервопривода» или «сервоприводом», термин не
  сработает — сохранённая форма термина должна встречаться в тексте как
  есть. Для языков с богатым словоизменением (в т.ч. русского) это значит,
  что термин иногда стоит добавлять в нескольких употребительных формах.
- Импорт TMX рассматривает каждый `<tu>` как один сегмент верхнего уровня и
  применяет то же правило «делить на предложения, только если счётчики
  совпадают», что и для пар документов (см. «Наполнение базы переводов»
  выше). Если исходный TMX уже сегментирован по-другому (например, по
  абзацам целиком или, наоборот, слишком мелко), это может дать более
  грубые или более дробные записи в базе, чем ожидалось — стоит проверить
  результат на вкладке «База переводов» после импорта.
- Backend не проверялся с реальной Ollama и GPU в среде разработки (в этом
  окружении нет видеокарты) — вся сетевая логика проверена тестами с
  подменённым клиентом, но перед первым реальным использованием стоит
  прогнать пару переводов вручную и свериться с ожиданиями.
